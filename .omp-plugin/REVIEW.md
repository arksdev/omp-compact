## P1 — высокий приоритет

### 1. Ошибка сохранения evidence не блокирует auto-shake

**Код:** [audit-lifecycle.ts:282](audit-lifecycle.ts#L282), [audit-lifecycle.ts:457](audit-lifecycle.ts#L457), [audit-lifecycle.ts:559](audit-lifecycle.ts#L559), [index.ts:1025](index.ts#L1025).

Ошибки completion/publish перехватываются и превращаются в успешно завершённый promise. Запись не получает признак неуспешного сохранения, а затем удаляется из `#records`. Между тем `#evidenceReady()` проверяет только `abandoned`.

Поэтому ошибка `persistMutation()` или `persistGit()` может оставить drain «успешным» и разрешить shake без сохранённого evidence. Если ошибка произошла до `snapshot()`, проблемная запись вообще не попадёт в проверку. Путь `edit` дополнительно сохраняет evidence вне `AuditLifecycle`.

**Что исправить:** сохранять результат публикации до завершения соответствующего logical run; любая ошибка сохранения должна закрывать shake-gate, включая синхронный путь `edit`.

### 2. Отложенный `agent_end` может запустить shake уже внутри следующего run

**Код:** [index.ts:1077](index.ts#L1077), [index.ts:1135](index.ts#L1135), [post-turn-shake.ts:222](post-turn-shake.ts#L222), [post-turn-shake.ts:262](post-turn-shake.ts#L262).

Сценарий: run A завершился, его audit ещё выполняется; пользователь запускает B. `beginRun()` уже переключает epoch и настройки на B. После завершения старого drain вызывается `onAgentEnd(A)`, но epoch захватывается **внутри этого позднего вызова**, то есть уже от B. Последующая проверка epoch проходит.

При включённом auto-shake с порогом `0` старое событие может вызвать переписывание истории во время B. Проверка `sessionManager` этого не предотвращает: внутри одной сессии объект тот же. Публичный `AgentSession.shake()` установленного хоста не добавляет проверку idle.

**Что исправить:** захватывать идентичность run до ожидания drain и проверять её перед dispatch, а не впервые внутри отложенного `onAgentEnd()`.

## P2 — ошибки поведения и достоверности

### 3. Асинхронное write-evidence привязывается к текущей ветви, а не к исходной

**Код:** [index.ts:706](index.ts#L706), [index.ts:1013](index.ts#L1013), [audit-lifecycle.ts:268](audit-lifecycle.ts#L268).

Post-image читается асинхронно, после чего вызывается обычный `pi.appendEntry()`. В хосте он создаёт запись с `parentId` **текущего** leaf.

Если за это время пришёл следующий запрос или пользователь перешёл через `/tree`, evidence старого вызова может оказаться в другой ветви. При восстановлении исходной ветви его уже не будет. Для stats похожая опасность прямо описана и частично учтена в `stageTerminalStats()`, но write-carrier такой привязки не имеет.

**Что исправить:** привязать публикацию к исходному run/branch boundary; смена ветви не должна молча перенаправлять старый carrier.

### 4. Post-image одного `write` может содержать результат следующей записи

**Код:** [audit.ts:473](audit.ts#L473), [audit.ts:485](audit.ts#L485), [index.ts:1013](index.ts#L1013).

Completion повторно читает файл по пути. Проверка тройного равенства canonical path защищает от смены адресата, но не от изменения содержимого того же файла.

Даже последовательные записи могут пересечься с audit: обработчик `tool_execution_end` запускает completion в фоне и возвращает управление. Следующий `write` способен изменить файл до чтения post-image предыдущего. Тогда первому вызову приписывается чужой diff с `exact: true`.

**Что исправить:** использовать post-image конкретного вызова либо отбрасывать точную атрибуцию при пересечении записей в один canonical target. Совпадения пути недостаточно.

### 5. `quietCommitHash()` может приписать новому коммиту старый hash

**Код:** [git-records.ts:783](git-records.ts#L783).

Проверяется, что после `commit` идёт подкоманда `log`, но её параметры и repository context не проверяются.

Например, при совпадающих subject команда `git commit -q -m "wip" && git log --skip=1 --oneline -1` даст hash предыдущего коммита, который функция представит как только что созданный. Аналогичные проблемы возможны с другим revision или `git -C`.

**Что исправить:** принимать fallback только для формы `log`, которая доказуемо показывает новый HEAD того же репозитория. Остальные формы оставлять без подтверждённого hash.

### 6. Цепочки через `;` ошибочно считаются успешными целиком

**Код:** [git-records.ts:323](git-records.ts#L323), [git-records.ts:525](git-records.ts#L525), [git-records.ts:830](git-records.ts#L830).

Токенизатор теряет различие между `&&`, `;` и разделением команд переводом строки. Затем общий `isError === false` превращает все Git-сегменты в успешные.

Для `git add missing-file; git status --porcelain` итоговый exit code может быть `0`, хотя `add` завершился ошибкой. Плагин покажет его как обычную успешную Git-строку, скрыв диагностический вывод Bash.

Это противоречит обоснованию в [context/git-command-grammar.md:7](../context/git-command-grammar.md#L7): проверка только общего error-path не покрывает раннюю ошибку с успешной последней командой.

**Что исправить:** сохранять семантику разделителей либо не утверждать успех отдельных сегментов без соответствующего доказательства.

### 7. `clear` теряет сводку коммитов прерванного run

**Код:** [runtime-adapter.ts:848](runtime-adapter.ts#L848), [render-decision.ts:170](render-decision.ts#L170), [render-decision.ts:213](render-decision.ts#L213).

Decision table разрешает итоговую Git-сводку для `clear + full`, но runtime вычисляет `terminalProjection` только для `filtered`.

В `full` передаются `hashesLength: 0` и отсутствие anchor. Исключение для коммитов не срабатывает, после чего правило `clear` скрывает строку.

Это нарушает явное обещание [README.en.md:132](../README.en.md#L132): созданные коммиты остаются видимыми даже после прерывания.

**Что исправить:** предоставлять проекцию и для терминального `clear + full`, не возвращая остальные диагностические строки.

### 8. Быстрые нажатия `alt+c` могут потерять шаги цикла

**Код:** [cycle-handler.ts:36](cycle-handler.ts#L36), [save-flow.ts:138](save-flow.ts#L138).

`load()` и вычисление следующего состояния выполняются **до** входа в сериализованную save-flow queue. Хост не ожидает завершения shortcut-handler перед следующим нажатием.

Два перекрывающихся нажатия могут прочитать `compact` и оба сохранить `live`, вместо перехода `compact → live → clear`.

**Что исправить:** сериализовать всю операцию «прочитать → вычислить следующий шаг → сохранить», а не только сохранение уже вычисленного snapshot.

### 9. Уже раскрытые skill/diagnostics карточки принудительно сворачиваются

**Код:** [runtime-adapter.ts:1678](runtime-adapter.ts#L1678), [runtime-adapter.ts:1697](runtime-adapter.ts#L1697).

Хост вызывает `setExpanded(toolOutputExpanded)` **до** добавления карточки в transcript. Плагин устанавливает wrapper позже и создаёт observed state как `{}`. Поэтому уже состоявшийся `setExpanded(true)` потерян, и карточка рендерится компактно до следующего переключения.

Это касается как минимум skill и late diagnostics. Для обычных tool-карточек начальное раскрытие учитывается отдельно, но общий leaf-helper этого не делает.

**Что исправить:** учитывать начальное состояние раскрытия; неизвестное состояние не приравнивать к collapsed.

### 10. Display-path snapshot общий для всех исторических run

**Код:** [runtime-session-state.ts:268](runtime-session-state.ts#L268), [runtime-session-state.ts:482](runtime-session-state.ts#L482), [runtime-adapter.ts:882](runtime-adapter.ts#L882).

`#displayPaths` хранится один на сессию и заменяется при новом run. Все старые состояния при перерисовке используют именно его, а не snapshot своего ledger.

После изменения `compactPaths` или cwd старые строки могут переименоваться при resize/replay. Это противоречит заявленной неизменности display options для logical run.

**Что исправить:** хранить display-path snapshot рядом с mode snapshot конкретного ledger.

### 11. Создание и удаление пустого файла не попадают в mutation-evidence

**Код:** [audit.ts:425](audit.ts#L425), [audit.ts:489](audit.ts#L489), [audit-diff.ts:325](audit-diff.ts#L325).

Создание пустого файла получает `before === after === ""` и считается отсутствием изменения. Удаление пустого файла получает `removed === 0` и тоже отбрасывается.

Но создание/удаление `.gitkeep` или пустого `__init__.py` — реальное изменение файловой системы. В `live` оно исчезнет из итогового mutation-журнала.

**Что исправить:** отличать отсутствие изменения текста от изменения существования файла. Нулевое число строк не делает создание или удаление no-op.

### 12. Отменённый session switch уже успевает разобрать плагин

**Код:** [index.ts:1191](index.ts#L1191), [context/session-switch-lifecycle.md:19](../context/session-switch-lifecycle.md#L19).

Для всех причин, кроме `fork`, `dispose()` выполняется в `session_before_switch`. Если более позднее расширение возвращает `{cancel: true}`, хост остаётся в прежней сессии и не посылает committed switch-event. Но adapter, audit и run state уже сброшены.

Это известный открытый случай, зафиксированный в `context/`; прежнее обоснование сохраняет тайминг, но не устраняет дефект.

**Что исправить:** разделить предварительную отмену фоновой работы и teardown после подтверждённого перехода либо восстанавливать состояние при отмене.

## P3 — дополнительные замечания

- **Лимит config не ограничивает чтение файла.** [config.ts:786](config.ts#L786), [config.ts:938](config.ts#L938): сначала весь файл читается в память, затем проверяются 65 536 байт. Большой файл создаёт лишнюю нагрузку до проверки; FIFO в синхронном startup-read способен заблокировать загрузку. Нужны проверка regular file и ограниченное чтение.
- **Узкий terminal обрезает mutation-counts.** [render.ts:355](render.ts#L355): при `head + tail >= width` всё равно выделяется минимум одна колонка под path. Строка превышает ширину, и финальный truncator хоста обрезает статистику справа — вопреки контракту этого helper. Для такой ширины нужен отдельный layout или перенос.

## Общая оценка и проверки исходного ревью (87b738a)

Переписывать архитектуру целиком не предлагается. **Own-instance descriptor patches, fail-open при неоднозначном binding и бюджеты diff/hydration — правильные решения.** Основной долг — согласовать между модулями владение run, ветвью и результатом публикации evidence; локальные guards пока не складываются в сквозную гарантию.

В рамках ревью выполнен только статический анализ:

- `bun run typecheck` — успешно;
- `bun run lint` — успешно, 149 файлов, без исправлений.

**Тесты и runtime-сценарии не запускались. Производственный код не изменялся.**
